# 평가: SimCity 3000 대신 cimulity를 쓰는 안

대상: [zeikar/cimulity](https://github.com/zeikar/cimulity) (MIT, 마지막 커밋 2026-09-22, 1인 개발).
평가일: 2026-10-10.
방법: 소스 코드를 직접 읽고, 시뮬레이션 코어를 **브라우저 없이(헤드리스)** 이 클라우드 환경에서 실행했습니다.
재현 스크립트: `experiments/cimulity/probe.ts`

## 무엇인가
- Next.js, TypeScript, PixiJS로 만든 브라우저용 SimCity풍 게임입니다. 64x64 아이소메트릭 맵을 씁니다.
- 할 수 있는 일: 도로, R/C/I 구역 지정, 발전소, 급수탑, 경찰·소방·병원·학교, 공원, 지형 편집, 속도 조절과 일시정지
- 시뮬레이션: 전력·급수 연결, 서비스 커버리지, 지가, 노동시장(일자리와 통근), 도로 혼잡, 쇠퇴, 월별 세수와 유지비, 행복도(표시용)
- 테스트 파일이 93개이고, 구조가 계층별로 나뉘어 있습니다. 코어는 렌더링(Pixi)에 의존하지 않습니다.

## 직접 확인한 것 (실행 결과)
| 항목 | 결과 |
|---|---|
| 헤드리스 실행 | `World` + `executeClick`/`executeDrag` + `tick()`만으로 동작. 브라우저와 화면이 필요 없음 |
| 속도 | 720틱(게임 시간 2년)을 약 0.36초에 처리 |
| 관찰 | 인구, 자금, 일자리, 실업, R/C/I 수요, 행복도, 세수, 유지비를 **정확한 숫자**로 읽음. `inspectTile`로 칸별 원인(전력·급수·커버리지·지가) 확인 |
| 행동 | 도구 명령의 성공 여부와 바뀐 칸을 결과로 돌려받음 |
| 진단 → 수정 | 발전소와 급수탑을 도로에 연결하지 않으면 6개월 뒤에도 인구가 0이고, `inspectTile`이 `powered=false`를 알려 줌. 연결하자 12개월 뒤 인구 125 |
| 결정성 | 같은 입력이면 같은 결과 (코어에 `Math.random` 없음) |
| 대안 비교 | 저장 상태(약 100KB)에서 두 갈래로 나눠 24개월을 실행. 아무것도 안 하면 인구 125, 서비스 4종을 지으면 인구 835. 다만 행복도는 0.672에서 0.615로 떨어짐. **절충이 실제로 존재** |

## SimCity 3000과 비교
| 기준 | SimCity 3000 (현재 경로) | cimulity |
|---|---|---|
| 관찰 | 화면 판독(OCR/비전, 오류 가능), 또는 미검증 플러그인 | 코드로 정확한 값 |
| 조작 | 마우스·키보드 자동화(불안정), 플러그인은 예산·속도만 확인 | 명령 API. 결과를 즉시 검증 가능 |
| 실행 환경 | 사용자 Windows PC 필수. 지금은 설치 위치조차 미확인 | 어디서나 실행. **이 클라우드에서 끝까지 직접 테스트 가능** |
| 비용 | 비전 호출 비용 | 관찰 비용 0. LLM은 전략 판단에만 사용 |
| 실험 속도 | 실시간 | 몇 년치를 1초 안에. 같은 상황을 반복 실험 가능 |
| 시뮬레이션 깊이 | 깊음: 세율, 부서 예산, 조례, 오염, 범죄, 재난, 대출, 이웃 거래 | 얕음: 아래 "한계" 참고 |
| 프로젝트 목표 적합성 | "실제 게임을 AI가 운영"에 그대로 맞음 | "AI 시장의 두뇌" 개발에 적합. 실제 게임 조작이라는 도전은 사라짐 |

## 한계 (중요)
- **정책 수단이 거의 없습니다.** 세율 조정, 부서별 예산, 조례가 없습니다.
  세율은 상수(`TAX_PER_POP`)이고, 예산 충당률은 결과값일 뿐입니다. 시장의 결정은 사실상 "어디에 무엇을 지을까"로 한정됩니다.
- **환경 지표가 없습니다.** 오염, 범죄, 재난이 없습니다 (코어에서 검색해도 나오지 않음). 사용자가 원한 "환경" 판단 요소가 빠집니다.
- **재정 압박이 약해 보입니다.** 시험 도시에서 세수 3,750에 유지비 422로 돈이 쉽게 쌓였습니다.
  자금은 0 아래로 내려가지 않고 빚도 없습니다. 이 결과는 작은 시험 도시 하나로 본 것이라 일반화하지 않습니다.
- 행복도는 표시용이라 시뮬레이션에 영향을 주지 않습니다.
- 1인이 활발히 개발 중이라 API가 바뀔 수 있습니다. 쓴다면 특정 커밋에 고정해야 합니다.
- 상태를 정확히 읽을 수 있으므로 "확인된 정보와 불확실한 정보의 구분"이 저절로 생기지 않습니다.
  관찰 범위를 일부러 제한하면(예: HUD 수준 지표와 표본 조사만 허용) 그 원칙을 유지할 수 있습니다.

## 결론과 권장
- **AI 시장의 두뇌(판단, 행동 검증, 결과 평가, 과거 결정 학습)를 만드는 개발 환경으로는 cimulity가 지금 더 낫습니다.**
  - 사용자 PC 없이 전체 루프를 실제로 돌리고 검증할 수 있습니다.
  - 저장 상태 분기로 "여러 대안 비교"를 실측으로 할 수 있습니다.
  - 비용이 거의 들지 않습니다.
- **SimCity 3000을 대체하기에는 시뮬레이션이 얕습니다.** 특히 세율·예산 정책과 환경 문제가 없습니다.
- 권장 방향: **cimulity로 두뇌를 먼저 만들고, SimCity 3000은 나중에 "어댑터"로 연결**합니다.
  - 현재의 상태 모델(값마다 출처와 확실성)과 기록 형식은 그대로 씁니다.
  - 게임별 차이는 `GameAdapter`(observe / act / advance)로 감춥니다.
  - cimulity 쪽은 Bun/Node로 도는 작은 JSON 브리지 하나와 Python 클라이언트면 됩니다.
- 정책 수단이 꼭 필요하면 포크해서 세율 같은 손잡이를 추가할 수 있습니다 (MIT 라이선스).
  다만 그러면 게임도 직접 설계하게 되므로 범위를 정해 두어야 합니다.
